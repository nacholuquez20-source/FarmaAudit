# FarmaAudit Frontend Handoff

This file tracks technical changes made by Codex so another agent or engineer can continue safely.

## Working Rules

- Do not create a new frontend project.
- Keep changes small, reversible, and scoped by stage.
- Preserve existing login and routes unless a stage explicitly changes them.
- Prefer the current stack: React, TypeScript, Tailwind, Supabase SDK, Vite.
- Validate frontend changes with:
  - `npm.cmd run lint`
  - `npx.cmd tsc -p tsconfig.app.json --noEmit`
  - `npm.cmd run build` when build output changes are acceptable.

## Current Baseline From Etapa 0

- The frontend lives in `frontend/`.
- Data flow is Google Sheets -> FastAPI sync -> Supabase -> React frontend via Supabase SDK.
- Existing routes: `/login`, `/dashboard`, `/sucursales`, `/sucursales/:id`, `/admin`.
- Existing primary data model for operational deviations is `gestion`.
- The frontend currently has TypeScript/lint blockers before new feature work:
  - Unused `Legend` import in `src/pages/Dashboard.tsx`.
  - Explicit `any` and caught-error lint issue in `src/lib/api.ts`.
  - React hook dependency warnings in `useReportes.ts` and `useGestion.ts`.
- Several user-facing Spanish strings have mojibake/encoding issues.
- Auth is implemented as a hook, but it is duplicated across route protection and layout usage.

### 2026-04-27 - Concordancia App Backend / Frontend

Files touched:
- `models.py`
- `supabase_setup.sql`
- `sync_sheets_to_supabase.py`
- `docs/CODEX_HANDOFF.md`

Key findings:
- Frontend and Supabase schema agree on the MVP tables after Etapa 2/3 SQL: `gestion`, `reportes`, `sucursales`, `auditores`, `control_stock`, `profiles`, `desvio_eventos`.
- The frontend introduced `Resuelta`, but backend `GestionState` and the initial SQL setup did not know that state.
- The backend sync is Sheets -> Supabase every 5 minutes. Without a guard, it could overwrite frontend status changes such as `En_proceso`, `Resuelta`, or `Cerrada` with older Sheet values.

Key changes:
- Added `RESUELTA = "Resuelta"` to backend `GestionState`.
- Updated `supabase_setup.sql` so a fresh install accepts `Resuelta`.
- Updated `sync_sheets_to_supabase.py` to preserve frontend-managed states (`En_proceso`, `Resuelta`, `Cerrada`) when the incoming Sheet state is still initial/passive (`Abierta`, `Vencida`, or empty).

Validation commands/results:
- `python -m py_compile models.py sync_sheets_to_supabase.py` passed.
- `npm.cmd run lint` passed.
- `npx.cmd tsc -p tsconfig.app.json --noEmit` passed.

Known risks:
- Frontend status changes are still not written back to Google Sheets. Supabase is now the operational source for status after the dashboard actions.
- If Sheets should remain the canonical source, the next step is adding writeback from Supabase/frontend actions to the `Gestion` sheet.
- The sync guard performs one select per gestion row. Fine for MVP, but should be optimized if the Gestion sheet grows large.

- Updated MVP README with the architecture decision.

- `npm.cmd run lint` passed.

Known risks:
- The WhatsApp bot still writes to Google Sheets first. Future migration should write new `reportes` and `gestion` records directly to Supabase.
